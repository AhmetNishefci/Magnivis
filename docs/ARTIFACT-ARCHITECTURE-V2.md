# Artifact Architecture V2 — canonical media and platform-aware delivery

This document owns prospective canonical binary identity and reference semantics. ARTIFACT-STORAGE.md continues to own Git durability/recovery; PLATFORM-QA.md owns presentation evidence; CREATIVE-DIRECTION.md owns story-specific execution. Priority: presentation quality, factual/editorial integrity, provenance/reproducibility, then storage efficiency.

**Create media according to presentation needs. Deduplicate only when resulting media is actually identical.** Existing media, renderers and storage convenience provide no advantage in discovery, creative selection or adaptation.

## Audited origin and historical decision

Review and authorized handoffs used different roots, and registration scripts retained each file set. The native artifact registry permitted multiple logical identities/paths with the same hash. Candidate and locked-master logical identities remain distinct records even when they refer to one path/hash. The missing original Wood Frog expectation remains missing; its accepted operational replacement remains separate. The V2 catalog indexes existing exact available bytes by reference, without transferring approval.

## MediaArtifact

src/artifacts/media.ts validates the file-backed artifacts/media-catalog.json. Each ordinary payload has ID `media.<full SHA-256>`, its exact hash, canonical repository-relative path, MIME type, byte size, provenance/source commit/source records, known or explicitly unknown creation time, and exact parent-media references for generation/adaptation. State and owner approval are absent from MediaArtifact. Existing native ArtifactManifest records retain their lifecycle/provenance truth.

Canonical means the one durable file chosen for a unique payload; it does not require renaming files into a hash directory. Existing meaningful master/audio/cover paths are retained. A prospective payload's ID/path/hash/size are immutable. A prospective platform adaptation requires exact generation-parent references to its approved master lineage. Changing bytes creates another artifact; changing state creates another workflow record/revision. Catalog registration reads existing generated bytes, validates provenance and relationships, and never copies/render-generates media. Removed/changed historical catalog rows fail the milestone validator.

All media references bind ID AND SHA. Resolution validates actual size/hash, source-record availability, repository containment (including symlinks), parents and exceptions. Ordinary duplicate SHA registration fails with the existing canonical identity/path. Cyclic lineage and stale references fail. Different bytes remain eligible regardless of why a platform needs them.

## PlatformVariant and delivery

New native PlatformVariants use `mediaArtifact: {id, sha256}` for the exact presentation payload. `sourceMaster` remains the approved editorial/production lineage; it is not automatically the selected upload payload. The existing safe-area derivative relationship remains valid; `platform-specific-derivative` additionally covers arbitrary presentation changes such as crop, encoding, caption position or framing. Shared transformed bytes can serve multiple variants without requiring a platform-owned binary identity. Existing technical/safe-area/editorial/human gates still apply.

Delivery Manifest V3 retains existing metadata, copy, readiness, media inspection and production-chain validation. Video and selected cover artifact entries carry canonical media references and repository paths. Package folders contain manifest.json, metadata.json, upload-copy.txt and review.md, plus an optional small accessibility VTT. V3 never copies video/cover payloads. It refuses to overwrite an existing handoff. A new lifecycle stage may create a new small manifest directory with the same media reference; review, readiness, locking and authorization do not create payloads.

V1/V2 packages remain readable with their original hashes and portable files. Legacy generation without a media reference remains a compatibility/ignored export-staging path; registering new durable copies is rejected by V2. New durable production handoffs use V3. An optional temporary export copy is not an independent durable media identity and must remain ignored; no persistent symlink/export hierarchy is introduced.

Manual upload resolution:

```sh
pnpm exec tsx scripts/resolve-delivery-media.ts <path/to/manifest.json>
pnpm exec tsx scripts/media-artifacts.ts verify
pnpm exec tsx scripts/media-artifacts.ts reference <existing/file>
pnpm exec tsx scripts/media-artifacts.ts register <provenance-bound-artifact.json>
```

The read-only resolver follows package → exact media reference (or a frozen legacy payload hash) → catalog → canonical file. It prints the exact repository/absolute upload path and hash. For V3, the native delivery validator additionally resolves PlatformVariant and its approved content/production chain. Legacy resolution is byte lookup, not a rewrite of the historical upload instruction/authorization.

## Authorization and actual publication

src/delivery/media-bindings.ts supplies an exact V2 publication-authorization binding to owner decision, variant revision/hash, ready delivery ID/hash and media identity. Its validator requires matching native owner approval; it neither grants human authority nor writes media. Owner decision evidence must be retained separately. PublicationRecord's optional `source.mediaArtifact` is required whenever its referenced variant has a media reference; the operations registry validates exact variant/hash/catalog bytes. The published-media validator also binds the actual record to the exact delivery manifest hash. Existing historical records remain readable unchanged.

An authorization is distinct from a PublicationRecord. Scheduling evidence is distinct from publication. No records/analytics are inferred from file presence or lifecycle readiness. Actual owner/platform publication evidence is required before recording publication. This architecture milestone creates no publication authorization or completed publication records.

## Audio, images, evidence and exceptions

The same payload rule applies to WAV/audio, generated images, selected covers and thumbnails: identical bytes can share canonical media while different artwork or sound remains distinct. Embedded images/audio are production dependencies, not automatically upload files. Small JSON, decision records and manifests are not the optimization target. Other large binary dependencies may use font or application/octet-stream MIME types when appropriate; font licenses remain independently preserved under asset provenance policy.

Frozen QA snapshots remain independent legacy evidence. Future independently retained identical evidence/compatibility copies require an explicit exception with reason, hash-bound decision record and exact `duplicateOf` reference. Exception IDs use `media.<SHA>.<purpose>` and do not replace the ordinary canonical payload. Evidence snapshot retention must be justified by provenance, not directory symmetry or lifecycle transitions. Changed evidence/compatibility decisions fail validation. No blanket exception based on an extension or platform exists.

## Integrity, recovery and limits

`pnpm exec tsx scripts/validate-artifact-v2.ts` runs schema/catalog/durability checks, freezes historical identities, validates scheduling evidence and the exact documentation amendment, and rejects any newly tracked media binary not represented by canonical media or an explicit exception. Renaming a known payload cannot bypass the hash check; unknown-format binary files of at least 1 MiB also require cataloguing. Small text/JSON is outside this optimization target. `pnpm check` includes this gate through the new regression suite; package.json remains exact because it is a locked render dependency. `pnpm artifacts:durable` combines the native artifact registry checks with canonical media checks. Artifact verify/restore checks canonical media directly: Git already supplies each canonical path, so no restore copy is required for it. Missing/corrupt canonical files fail; missing historical expectations remain explicit.

An isolated Git archive/checkout test resolves every catalog entry and all four Chocolate upload identities without workstation caches or media generation. This tests exact retrieval, not byte-identical regeneration or real-device presentation.

No garbage collection/deletion tool is added. Do not delete media referenced by a variant, delivery, authorization, publication, parent relationship, historical binding or evidence exception. Future cleanup requires a separate dependency audit and owner authorization. Remote durability remains current Git policy, without new cloud storage, LFS, queues or publishing automation.

Adaptive Creative Direction, af_heart primary narrator, adaptive captions/sound, story-led duration, open-world discovery, quality-first approximately one unique short/day and provisional 20:00 Kosovo window remain unchanged. Platform-specific presentation quality remains an independent human review concern; canonical reuse cannot imply a device/UI pass.

## Owner-authorized historical failed-media retention

Cycle #8's retention-contract repair distinguishes immutable payload identity from production eligibility. Catalog entries remain unchanged. `artifacts/media-retentions.json` indexes hash-bound historical dispositions in `src/artifacts/retention.ts`; this is lifecycle/storage evidence, not a new media identity or a duplicate-media exception. Admission requires the exact original production event and candidate, journaled owner revision/rejection, explicit scoped retention authority, failure/rejection evidence, and any replacement's later production event. The current committed candidate of every cycle must be different. A filename, hash, extension, age or self-declared status never grants retention eligibility.

Historical bytes may be durably stored as ordered exact byte parts under `artifacts/historical-media/`. Each part has a bounded physical Git file size, SHA-256, byte count and offset; concatenation must reproduce the original catalog identity and size exactly. Parts are archive storage, never production media or upload assets. The original canonical path remains the unchanged identity and an ignored materialization; existing bytes are never modified. If absent, historical resolution verifies the archive and authority, then restores exact bytes without rendering, encoding or overwriting. Missing/corrupt archive parts, changed evidence, original-byte corruption or an active retired candidate fail validation. No prior approved historical media is moved into this storage.

Active/canonical production media and every new registration remain subject to the exclusive100MiB limit and full identity/provenance/Git durability checks. Prospective variants, delivery resolution and current/pending workflow states reject retained media. Replay can inspect the historically invalid candidate before its journaled revision; live-head validation cannot accept it again. Parent provenance may reference historical bytes without transferring production eligibility. Physical archival parts also remain strictly below100MiB. This implements the owner's historical-preservation repair; it does not exempt or split an oversized active candidate to make it publishable.
